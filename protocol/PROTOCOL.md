# Tab-D protocol v1

Both USB (ADB reverse to Mac loopback 49832) and LAN (49833) use the same TLS stream. The Android peer pins SHA-256 of the complete DER leaf certificate, checks certificate validity, then authenticates a privately provisioned random token inside TLS. Development pairing is stored outside the bundles, mode 0600, and provisioned through the authorized USB debugging channel. Tokens and private keys must never enter logs or Git.

Each packet starts with a UInt32 big-endian length including its one-byte packet type, followed by payload. Maximum length: 8 MiB. Inbound control JSON is limited to 64 KiB. Multiple peers are rejected; queued outgoing data is bounded and a congested connection is closed rather than dropping H.264 dependencies silently.

| Type | Payload |
|---|---|
| 1 | UTF-8 control JSON |
| 2 | UTF-8 `videoConfig` JSON |
| 3 | epoch UInt32 + sequence UInt64 + presentation timestamp microseconds UInt64 + flags UInt8 + Annex B H.264 access unit |

All integers are big-endian. Video flag bit 0 marks a keyframe. `videoConfig` carries `epoch`, `width`, `height`, `csd0`, `csd1`, and verified `hardware`; CSD strings are Base64 SPS/PPS including four-byte Annex B prefixes. Config precedes frames. `decoderReady` requests a fresh keyframe, including on a static desktop.

Client hello: `{type:"hello",version:1,token,visible,device}`. Since 0.6.1, `hello.device` carries the Android system device name (model fallback), and `helloAck.device` carries the Mac system computer name. These optional display-only strings are stripped of control characters and limited to 128 characters; absent names use generic platform labels. They are not authentication identities. Server validates it before sending `helloAck` and authoritative `status`. Client commands: `start`, `pause`, `resume`, `disconnect`, `decoderReady`, `keyframe`, `presented`, `click`, `pointer`, `scroll`, `ping`. Server responses: `pauseAck`, `disconnectAck`, `clickResult`, `pointerResult`, `scrollResult`, `pong`, and `status` (`ready`, `starting`, `streaming`, `paused`, `stopped`, `error`). `decoderReady` and `keyframe` must include the current epoch; stale or missing epochs are ignored. Presentation messages include epoch and sequence. A 12-second readiness deadline starts when the Mac begins a session, including display settlement and capture startup. Receiving the matching `decoderReady` replaces it with the presentation deadline. The first matching `decoderReady` triggers an immediate cached-screen IDR and at most two additional startup IDRs after 100ms and 300ms if no frame has been presented. Epoch changes, pause and successful presentation cancel these retries. No presentation within three seconds of readiness fails the start and removes the display; duplicate readiness messages do not extend this deadline.

Mac owns display lifetime. Pause invalidates the media epoch and stops capture/encode, but keeps the virtual display. Pause acknowledgement follows media shutdown. A confirmed paused display survives transport loss and Android process death. Resume reuses that display with a new epoch. An explicitly ended session cannot be resumed automatically. Unexpected active connection loss enters recovery for three seconds, then removes the display; stale recovery callbacks cannot remove a resumed/paused display. Android's system Home lifecycle pause is best effort; the explicit return button waits for acknowledgement before moving the Tab-D task to the background.

## Host interruption and wake recovery (0.6.0)

Packet framing, authentication and `version:1` are unchanged. `hello.visible` is an optional boolean, defaulting to `false`; it reports whether the authenticated Android Activity is visible on this transport. Mac automatic wake capture requires a current authenticated peer whose visibility has been confirmed by `hello.visible:true` or an explicit foreground `resume` request. A reconnect alone cannot authorize background capture. An older client omitting visibility does not receive automatic wake capture solely from reconnecting.

Authoritative `status` adds optional boolean fields `hostSuspended` and `hostRecovering`, each defaulting to `false` when absent. `hostSuspended:true` means at least one host interruption remains active: system sleep, display sleep, inactive user session or screen lock. `hostRecovering:true` means the host has pending streaming recovery and no active interruption. They describe host availability and recovery intent, not proof that a frame has been presented. The `state`, `displayID` and epoch remain authoritative for session/display/media state. Clients must ignore unknown fields; the wire change does not guarantee equivalent wake behavior with older applications. Wake recovery is validated against Mac and Android 0.6.0 together.

Mac retains the virtual display, invalidates the media epoch, releases held input and stops capture/encoding during a host interruption. Interruption reasons can overlap; one wake notification cannot clear another reason. The three-second ordinary active-transport loss cleanup does not remove a display held by host suspension or pending wake recovery. An explicit disconnect clears session intent and cancels pending recovery even if capture shutdown is already underway. Later wake notifications cannot recreate an explicitly ended display.

After all host interruptions clear, Mac closes the old peer and restarts its TLS listeners. Listener readiness is checked with at most three start attempts. Streaming recovery requires prior streaming intent and a visible authenticated peer, reuses the retained display with a new epoch, and permits at most three capture attempts. A prior Android background pause remains paused until the user returns. Capture content discovery and start each have a six-second wait limit, and capture stop has a two-second wait limit. Obsolete asynchronous completions are rejected; these limits bound application waiting and do not guarantee that macOS has completed an unresponsive framework operation. Normal session readiness and first-presentation deadlines remain in force.

On each new transport, Android waits for the first authoritative `status` after `helloAck` before automatically sending start/resume. A suspended status stops local media/input while preserving prior display intent. After suspension or initial reconciliation, a retained `paused` display may resume only with prior intent and a visible Activity; `ready`/`stopped` may automatically start only with both `hostRecovering:true` and prior intent. Ordinary background pause is not a wake request, and a host stop without recovery intent cannot resurrect a session. An already `starting`/`streaming` host is reconciled without duplicate starts. Android imposes a five-second wait for the initial status and start/resume control response; an unanswered request shows manual retry guidance rather than an unbounded retry loop. This is separate from Mac's video-presentation deadlines. Backgrounding, disconnect and transport replacement cancel the pending control wait.

Host screen-lock detection also uses undocumented macOS distributed notifications and a private session dictionary key. A polled `true` lock flag can add a blocker; only an explicit unlock notification clears it. Session inactivity is not synonymous with screen lock. `CGDisplayIsAsleep` is not used to clear display-sleep blockers because polling can race asynchronous workspace notifications. Missed or changed OS notifications may therefore require manual recovery; no timer assumes that the Mac has unlocked.

## Click and drag input

An authenticated client sends a type-1 control packet `{type:"click",id:"<UUID string>",epoch,x,y,button?:"left"|"right",clickCount?:1|2}`. `id` is a canonical 36-character UUID string. `epoch` must be an integer in the UInt32 range, and `x` and `y` must be finite numbers in `[0,1]`, not booleans. Coordinates refer to the fitted video Surface, with origin at its top left, x increasing right and y increasing down. The Mac maps them to its owned display's current CG bounds as `(minX + x*(width-1), minY + y*(height-1))`, keeping endpoint coordinates inside that display.

The Android client interprets a short single-finger contact as left click, stationary contact lasting 500ms as exactly one right click, and movement past touch slop before that deadline as a left drag starting at the original DOWN position. A completed right click never generates a left click on lift. Dragging suppresses long-press. Input requires foreground, authentication, streaming the current epoch, valid Surface and hidden control bar. A second pointer cancels single input before starting vertical scroll; a third pointer or system cancellation cancels input. A Surface tap beginning with the control bar open only closes the bar. Android Back toggles the bar and cancels any drag or scroll.

The optional click `button` defaults to `left`; only `left` and `right` are valid. Optional `clickCount` (0.4.0) defaults to 1 and accepts only the integer 1 or 2, never booleans; right clicks require 1. Both use a cursor move and matching down/up events. Clicks during a held drag are rejected.

The Mac accepts clicks only from the connected authenticated peer while its session is streaming the same epoch and is not stopping. The target must still be the owned active non-mirrored virtual display. A bounded cache rejects the most recent 128 duplicate UUIDs within an epoch. Invalid field types/ranges are dropped; parsed requests receive `{type:"clickResult",id,epoch,accepted,message}`, with the parsed UUID normalized to lowercase. The response retains the request epoch, including on rejection. Paused, stale, disconnected, duplicate and unavailable-display requests are rejected rather than replayed on resume.

Posting the cursor move and button down/up requires macOS post-event permission, exposed to the user in **Privacy & Security → Accessibility / 손쉬운 사용**. Denial returns `accepted:false` and an actionable message without ending video. Events use a private source, empty modifier flags and the validated click count (drags always use 1). `accepted:true` means the Mac passed its checks and posted the events; it does not acknowledge that another application performed a particular action. Android matches both UUID and current epoch, keeps at most 16 pending requests, and treats an unanswered request as timed out after three seconds without retrying the click. Epoch invalidation clears pending requests.

Input behavior was added on 2026-10-18. Its separate real-device input results are recorded in `docs/validation/README.md`; earlier video/lifecycle PASS results do not establish pointer-input correctness.

## Ordered drag lifecycle (0.3.0)

A type-1 `{type:"pointer",phase:"begin"|"move"|"end"|"cancel",id,epoch,sequence,x,y}` uses the same UUID, epoch and normalized coordinate validation as clicks. All phases require coordinates. Sequence is UInt32: begin must be 0 and subsequent messages strictly increase for the same gesture and epoch. Begin posts left down at the original contact, move posts leftMouseDragged, and end flushes the final position then posts left up. Cancel releases at the last delivered point. There is only one held gesture; foreign/stale IDs, reorder, duplicates, missing begin and recently replayed begin IDs are rejected. A bounded 128-ID cache is scoped to the epoch. Session, owned display and Accessibility gates also apply to drags.

Lifecycle responses `{type:"pointerResult",id,epoch,phase,accepted,message}` acknowledge begin/end/cancel, never moves. Android correlates UUID/epoch/phase, bounds pending requests, times out after 3s and cancels a rejected or timed-out begin without retry. Moves are coalesced to the latest point at intervals of at least 17ms; terminal messages follow the pending final move. A stationary drag sends a move keepalive every 500ms. Mac releases after 2s without valid gesture activity, on pause, epoch replacement, disconnection, display loss, permission loss, error or app shutdown. Cleanup attempts button-up even when permission has been revoked; OS permission enforcement still applies. Unknown old cancel messages cannot release a newer gesture. Current v1 packet framing and authentication remain unchanged.

## Double taps (0.4.0)

The first short left tap posts one down/up pair immediately with clickCount 1. Android recognizes a nearby second short tap using the platform double-tap timeout and scaled double-tap slop, in Surface pixel coordinates. It sends only the second pair with clickCount 2; it never sends an additional complete two-pair sequence. Mac applies this count to `mouseEventClickState` on both down and up, including mouse-up retry. Each request keeps its own UUID and the existing duplicate/session/permission guards. Slow or distant taps stay single clicks; a completed pair resets the sequence so a third tap starts at 1. Drag, right click, cancellation, menu and lifecycle/Surface/epoch changes reset tap grouping. The authenticated Android peer owns physical touch timing; Mac does not infer it from network arrival timing. Pointer lifecycle packets cannot specify clickCount 2.

## Vertical two-finger scroll (0.5.0)

Type-1 `{type:"scroll",id,epoch,x,y,deltaY}` is one independent wheel delta, shared by USB and LAN. Every batch gets a fresh UUID. `x`/`y` are the latest centroid normalized to the video Surface, in [0,1]. `deltaY` is finite, nonzero and in [-1,1], normalized by Surface height; positive means fingers moved down. Booleans and numeric strings are rejected. Mac resolves the anchor against the current owned display bounds and multiplies deltaY by its logical height. Fractional pixels accumulate within the epoch/mode; whole pixels are posted as continuous CG pixel wheel events with no momentum phase. Content follows finger direction. There is no horizontal or inertial scrolling.

Mac requires the authenticated peer, current streaming epoch, active owned non-mirrored display, no held drag, and Accessibility permission. A bounded 128-ID epoch cache rejects replay. Each validly parsed batch gets `{type:"scrollResult",id,epoch,accepted,message}`, including rejection; Android correlates UUID/epoch, bounds outstanding batches to 32, times out after 3s and never retries wheel movement. Rejection opens guidance without stopping video. Lifecycle and epoch/mode changes reset fractional residue.

Android tracks exactly two pointer IDs, independent of event index order, and starts after vertical centroid displacement exceeds platform touch slop. The first delta includes accumulated displacement. Historical samples are processed in order; 17ms coalescing sums deltas and retains the newest anchor. POINTER_UP includes final positions, which are processed and flushed before ending the pair. Single input stays suppressed until all fingers lift. A held left drag is cancelled first in the same TLS writer FIFO before any scroll packet. Third pointers, system cancellation, Back, Home, invalid Surface/session and epoch changes discard pending movement. Stationary or purely horizontal two-finger contact generates neither scroll nor right click.
